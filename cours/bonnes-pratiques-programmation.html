Les bonnes pratiques de programmation

Un cours transversal — Java, Python, JavaScript et autres langages — pour apprendre à bien programmer, pas seulement à faire fonctionner un programme.

01

Introduction

Un langage permet de faire fonctionner un programme. Le génie logiciel permet de construire un programme que l'on peut comprendre, tester, debugger, maintenir et faire évoluer.

Python est facile à prendre en main. Mais écrire rapidement du code qui fonctionne n'est pas la même chose qu'écrire du logiciel maintenable. Plus le langage laisse de liberté au développeur, plus les conventions, la lisibilité, le typage explicite, les tests et l'architecture deviennent importants.

🏸 Python

Prise en main rapide → on s'amuse rapidement → beaucoup de liberté → les contraintes arrivent progressivement

🎾 Java

Plus de technique dès le départ → typage, compilation, POO, interfaces, exceptions, JVM → cadre plus contraignant

🏓 C++

On entre directement dans le technique → compilation, typage fort, pointeurs, références, mémoire, POO, templates…

02

Philosophie du cours

Principe Le compilateur/interpréteur doit comprendre notre code. Mais surtout, un autre développeur doit pouvoir le comprendre.

Un code peut compiler, s'exécuter correctement et produire le bon résultat… et pourtant être mauvais. Les bonnes pratiques servent notamment à améliorer :

  • la lisibilité
  • la maintenabilité
  • le débogage
  • la testabilité
  • la réutilisabilité
  • l'évolutivité
  • la collaboration entre développeurs
À retenir Une bonne pratique doit toujours être accompagnée de son « pourquoi ». Éviter de présenter les règles comme des interdictions arbitraires.
03

Lisibilité du code

Une instruction par ligne, des noms explicites, les conventions du langage : autant de choix qui déterminent si le code se lit d'un coup d'œil ou se déchiffre.

Une instruction par ligne

❌ À éviter
int result = Integer.parseInt(getVariable())
    + getIncrement() / magicNumber.doubleValue();
✓ À privilégier
double variable = getVariable();
int increment = getIncrement();
double magicValue = magicNumber.doubleValue();

int value = Integer.parseInt(variable);
int result = value + increment;
Pourquoi ? Une instruction par ligne permet de lire le code étape par étape, de poser un breakpoint, d'inspecter les variables, d'identifier précisément l'instruction qui échoue et de comprendre plus facilement une stacktrace.

Le compilateur comprend une grosse ligne. Le développeur qui doit la debugger vous remerciera si vous l'avez découpée.

Éviter les chaînes d'appels inutiles

❌ À éviter
result = calculate(getValue().trim()
    .toLowerCase().replace(...));
✓ À privilégier
String value = getValue();
String trimmedValue = value.trim();
String normalizedValue = trimmedValue.toLowerCase();

result = calculate(normalizedValue);

Cela augmente légèrement le nombre de lignes, mais améliore fortement la compréhension et le debugging — chaque étape peut être inspectée séparément.

Donner des noms explicites aux variables

❌ À éviter
int x;
int n;
int v;
✓ À privilégier
int numberOfAttempts;
int numberOfUsers;
int currentValue;

x est rapide à écrire. numberOfAttempts est rapide à comprendre. Le nom d'une variable doit permettre de comprendre ce qu'elle représente sans devoir lire tout le code autour.

Respecter les conventions de nommage du langage

Java
class UserManager

private int numberOfUsers;

public void calculateStatus()
Python
class UserManager:

    number_of_users = 0

    def calculate_status():
        ...

Utiliser les conventions de l'écosystème : camelCase, PascalCase, snake_case, pour les constantes, attributs, variables locales, méthodes, classes. Le code doit avoir le dialecte du langage dans lequel il est écrit.

Utiliser l'anglais dans le code

Privilégier l'anglais pour les noms de classes, méthodes, variables, constantes, commentaires techniques et la documentation du code — et éviter les accents dans les identifiants. Le code est souvent partagé entre des personnes de nationalités différentes et avec des outils, frameworks et bibliothèques utilisant majoritairement l'anglais.

❌ À éviter
int nombreDeTentatives;
✓ À privilégier
int numberOfAttempts;
À retenirLe code parle anglais. Les explications peuvent parler français.
04

Faciliter le debugging

Une stacktrace vous donne une ligne. Donnez-lui une chance de vous donner une information utile.

Si une exception indique NullPointerException — MyClass.java:40 et que la ligne 40 contient dix opérations imbriquées, il faut déterminer quelle opération est responsable. Avec des variables intermédiaires, chaque étape peut être inspectée :

String value = getValue();
int increment = getIncrement();
double result = calculate(value, increment);

Réutiliser une valeur calculée

❌ À éviter
while (calculateStatus()) {
    ...
}
✓ À privilégier
boolean status = calculateStatus();

while (status) {
    ...
}

calculateStatus() appelée à chaque itération peut être volontaire — mais il faut se poser la question : la valeur doit-elle réellement être recalculée à chaque tour ? Réutiliser la valeur gagne en lisibilité et en possibilité d'inspection.

05

Responsabilités et découpage

Une fonction ou méthode devrait avoir une responsabilité clairement identifiable.

❌ À éviter
testIfOkAndDestroy();
✓ À privilégier
boolean isValid();
destroy();

Le nom testIfOkAndDestroy() révèle déjà un problème : la méthode semble faire au moins deux choses. Une méthode doit idéalement pouvoir être décrite par « Cette méthode fait X. » — et non « Cette méthode vérifie X, modifie Y, sauvegarde Z et détruit W. »

Éviter les fonctions trop longues

Une fonction longue est souvent le signal qu'elle contient plusieurs responsabilités. Découper permet de mieux lire, de mieux tester, de réutiliser certaines parties, de localiser les erreurs et de faire évoluer une partie sans modifier tout le reste.

06

Conditions et structures de contrôle

Décomposer les conditions complexes

❌ À éviter
if (value > 10 && status == ACTIVE
    && user != null && user.isAuthorized()) {
    ...
}
✓ À privilégier
boolean validValue = value > 10;
boolean active = status == ACTIVE;
boolean validUser = user != null;
boolean authorized = user.isAuthorized();

if (validValue && active && validUser && authorized) {
    ...
}

Les variables intermédiaires permettent de comprendre chaque condition, de debugger et de tester chaque élément séparément — lorsque cela améliore réellement la compréhension.

À retenirUne condition doit être lisible avant d'être compacte. Si une condition nécessite plusieurs secondes pour être comprise, elle mérite probablement d'être décomposée.

if : privilégier la simplicité

❌ À éviter
if (isActive == true) { ... }
// Python
if is_active == True: ...
✓ À privilégier
if (isActive) { ... }
# Python
if is_active: ...

Lorsque la variable est déjà un booléen, la comparaison à true est redondante.

Choisir la bonne structure de contrôle

Une longue succession de conditions n'est pas toujours la meilleure solution. Pour plusieurs égalités sur une même valeur, préférer une structure de sélection lorsque le langage en fournit une :

❌ À éviter
if (value == 1 || value == 2 || value == 3) {
    doSomething();
} else if (value == 4) {
    doSomethingElse();
}
✓ À privilégier
switch (value) {
    case 1: case 2: case 3:
        doSomething();
        break;
    case 4:
        doSomethingElse();
        break;
}
// Python moderne
match value:
    case 1 | 2 | 3:
        do_something()
    case 4:
        do_something_else()
À retenirChoisir la structure qui exprime le mieux l'intention.
07

Gestion des retours de fonction

Pour les fonctions contenant une logique métier, privilégier un point de sortie unique.

La valeur de retour est initialisée avec une valeur par défaut en début de fonction, puis modifiée selon les conditions rencontrées ; le return est placé en fin de fonction.

✓ Exemple recommandé
function getDiscount(age) {
    let discount = "Full price";

    if (age <= 18) {
        discount = "50% OFF";
    } else if (age >= 65) {
        discount = "30%";
    }

    return discount;
}

Pourquoi ce choix ?

  • Faciliter le débogage — la variable de résultat peut être observée dans l'inspecteur et suivie pas à pas au fur et à mesure de l'exécution.
  • Faciliter la maintenance — éviter de disperser des valeurs de retour littérales dans différentes branches ; nommer les constantes métier.
  • Faciliter la lecture du flux — un point de sortie unique permet de visualiser l'état initial du résultat, les règles qui peuvent le modifier, et la valeur finalement retournée.
❌ Valeurs dispersées
function calculateStatus(data) {
    if (conditionA) { return "ERROR_A"; }
    if (conditionB) { return "ERROR_B"; }
    return "OK";
}
✓ Sortie unique + constantes
const STATUS_OK = "OK";
const STATUS_ERROR_A = "ERROR_A";
const STATUS_ERROR_B = "ERROR_B";

function calculateStatus(data) {
    let status = STATUS_OK;
    if (conditionA) { status = STATUS_ERROR_A; }
    else if (conditionB) { status = STATUS_ERROR_B; }
    return status;
}

Tests unitaires et couverture

Un point de sortie unique ne signifie pas qu'il suffit de tester le return final : chaque branche métier doit être couverte.

test("minor gets 50% discount", () => {
    expect(getDiscount(18)).toBe("50% OFF");
});
test("senior gets 30% discount", () => {
    expect(getDiscount(65)).toBe("30%");
});
test("adult pays full price", () => {
    expect(getDiscount(30)).toBe("Full price");
});
Exception — retours anticipés (guard clauses) La règle ne doit pas être appliquée de manière dogmatique. Un retour anticipé peut être pertinent lorsqu'il permet de traiter immédiatement un cas invalide, exceptionnel ou non pertinent, et d'éviter une imbrication excessive. 
function processUser(user) {
    if (!user) { return; }
    if (!user.isActive) { return; }
    // Traitement principal
}
Retour d'expérience Cette règle est issue d'une expérience concrète de maintenance de code. Des valeurs retournées directement et dispersées peuvent sembler simples au moment du développement, mais deviennent plus difficiles à analyser et à faire évoluer lorsque la logique métier se complexifie. Reprendre un code plusieurs mois plus tard, le déboguer et le modifier sans régression est un critère de qualité au même titre que la fonctionnalité initiale.
08

Éviter la duplication

Si le même code apparaît plusieurs fois, se demander : pourquoi cette logique existe-t-elle à plusieurs endroits ?

La duplication augmente le risque d'incohérence. Si une règle métier change, il faudra modifier plusieurs endroits. Chercher à centraliser les comportements communs.

09

Valeurs, structures de données et mémoire

Éviter les valeurs magiques

❌ À éviter
if (temperature > 75) { ... }
✓ À privilégier
final double MAX_TEMPERATURE = 75;

if (temperature > MAX_TEMPERATURE) { ... }

Que représente 75 ? Le nom donne immédiatement du sens à la valeur — même principe pour les seuils, durées, tailles, codes, états, nombres utilisés plusieurs fois. Un nombre sans nom est souvent une information sans contexte.

Liste Python vs tableau Java

values = [70] crée une liste contenant un seul élément de valeur 70. Pour créer 70 éléments initialisés à 0 : values = [0] * 70. La liste reste cependant dynamique (values.append(42) → 71 éléments).

En Java, int[] values = new int[70]; crée un tableau de 70 éléments à taille fixe, chaque élément primitif recevant sa valeur par défaut (0, 0.0, false, null pour les objets).

AttentionUne liste Python n'a pas une taille fixe. values = [None] * 70 crée bien 70 éléments, mais append() peut ensuite agrandir la liste. Une liste Python n'est pas non plus l'équivalent exact d'un tableau Java : elle peut contenir des objets de types différents. Pour des données numériques homogènes et volumineuses, numpy.ndarray est souvent plus adapté.

Types primitifs, wrappers et génériques

Une abstraction plus générique n'est pas toujours la meilleure solution. Utiliser des wrappers (Integer, Double, Number…) simplifie souvent le développement, mais peut avoir un coût mémoire important sur de très grandes quantités de données :

Représentation objet
List values = new ArrayList<>();
Représentation primitive
double[] values = new double[size];

Dans le premier cas, les éléments sont des objets accessibles via des références ; dans le second, les valeurs sont stockées directement. Pour des volumes importants — par exemple des données scientifiques issues de longs scans — la différence peut devenir considérable : consommation mémoire, allocations, pression sur le Garbage Collector, performances, fluidité d'une IHM, risque d'OutOfMemoryError.

À retenir La généricité est un outil, pas une fin en soi. La simplicité d'utilisation d'un wrapper doit être mise en balance avec son coût réel lorsque les volumes deviennent importants. Ne pas optimiser prématurément, mais ne pas ignorer les caractéristiques mémoire des structures de données. Mesurer avec un profiler (par exemple Java VisualVM) avant et après l'optimisation permet de vérifier que l'amélioration est réelle.
10

Commentaires et documentation

Un commentaire ne doit pas simplement répéter le code — il doit expliquer le pourquoi.

❌ Peu utile
// Increment i
i++;
✓ Plus utile
// Retry three times because the PLC may need
// a few milliseconds to update its state
// after the command.
retryCount++;

Commenter les algorithmes complexes

Pour un algorithme difficile à comprendre : expliquer le principe, les hypothèses, les choix particuliers, et éventuellement donner une référence. Privilégier l'anglais dans les commentaires techniques.

11

Testabilité et maintenabilité

Une bonne architecture facilite les tests. Se demander : puis-je tester cette méthode indépendamment ? Fait-elle trop de choses ? Puis-je contrôler ses entrées, vérifier sa sortie, reproduire facilement un cas d'erreur ?

Pourquoi ?Si une fonction est difficile à tester, elle est parfois difficile à comprendre parce qu'elle fait trop de choses.

Le vrai test d'un programme n'est pas seulement « Est-ce qu'il fonctionne aujourd'hui ? » mais aussi « Est-ce qu'une autre personne pourra le modifier dans six mois sans avoir peur de casser quelque chose ? »

Penser au développeur de demain

Quand on écrit du code, trois personnes peuvent avoir besoin de le comprendre :

1. Celui qui l'écrit

2. Celui qui le maintient

3. Celui qui le débogue à 17h30 un vendredi soir

La troisième personne est souvent celle qu'il faut garder en tête.

12

Abstraction, interfaces et architecture

Programmer contre une abstraction, pas contre une implémentation.

PrincipeLe code métier doit dépendre de ce dont il a besoin, pas de ce qu'il n'a pas besoin de connaître.
❌ À éviter
ArrayList list = new ArrayList<>();
✓ À privilégier
List list = new ArrayList<>();
// L'implémentation peut être remplacée :
List list = new LinkedList<>();
// sans modifier le code qui manipule la liste.
Pourquoi ?Si l'architecture impose plus tard une autre implémentation, il faudra rechercher et modifier toutes les dépendances à ArrayList. Plus une dépendance à une implémentation est localisée, plus le logiciel est facile à faire évoluer.
